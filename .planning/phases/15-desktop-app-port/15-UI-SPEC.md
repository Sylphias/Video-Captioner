# Phase 15 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope note:** This phase's new UI surface is small and utilitarian — an Electron shell wrapping the existing, fully-styled web app. This contract covers ONLY the four new surfaces this phase introduces: (1) splash/loading window, (2) first-run Python/CUDA env setup flow, (3) settings screen (HF token + media-root picker), (4) model-download progress. Existing app pages (SubtitlesPage, ProjectsPage, AnimationBuilderPage) are out of scope and are not respecified — every value below is either read directly from the codebase's existing design system or is a discretionary default that follows its established conventions.

---

## Design System

| Property | Value |
|----------|-------|
| Tool | none — no component library, no Tailwind, no shadcn. Locked at Phase 01-03: "Co-located `.css` files per component (not CSS modules, not styled-components) — keeps tooling minimal." This phase's new surfaces MUST follow the same pattern: one `.tsx` + one co-located `.css` file per component, BEM class naming (`block__element--modifier`). |
| Preset | not applicable — shadcn gate skipped deliberately; introducing a component library 14 phases into a hand-rolled CSS codebase would break visual consistency, which is the opposite of this agent's mandate. |
| Component library | none — hand-rolled React function components |
| Icon library | none — the app is text-first. The only existing SVG usage is `UploadZone.tsx` (drag-and-drop icon). New surfaces should stay text/label-first; use a single small inline SVG only where a glyph is unavoidable (e.g. a settings gear button in the header) and keep it stroke-only, `currentColor`, no library import. |
| Font | System stack via `--font-family` token: `-apple-system, BlinkMacSystemFont, 'Segoe UI', Roboto, sans-serif`. On Windows (this phase's only target per D-06) this resolves to Segoe UI. |

## Spacing Scale

Declared values — these are the actual tokens already defined in `packages/frontend/src/styles/tokens.css`. Do not invent new spacing tokens for this phase's surfaces; compose from these five.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`--spacing-xs`) | Icon gaps, inline padding, progress-track corner radius |
| sm | 8px (`--spacing-sm`) | Compact element spacing, button padding-y, form-field gaps |
| md | 16px (`--spacing-md`) | Default element spacing, dialog body/header/footer padding |
| lg | 24px (`--spacing-lg`) | Section padding, header horizontal padding |
| xl | 32px (`--spacing-xl`) | Layout gaps, page padding |
| 2xl | 48px | Not defined in codebase — not needed for this phase's compact surfaces (splash window, settings dialog, progress cards are all small/dense). Do not introduce. |
| 3xl | 64px | Not defined in codebase — same as above; ProjectsPage empty-state uses `64px` as a literal, not a token, for its own vertical padding only. Do not introduce a new token; if a comparable empty/setup state needs this much breathing room, use the literal `64px` value exactly as ProjectsPage does, not a new custom property. |

Exceptions: none. Mouse/keyboard-only desktop app — no 44px touch-target minimum applies (no touchscreen target for this phase).

## Typography

Existing tokens from `tokens.css`, reused as-is — 4 sizes, 2 weights (within contract limits).

| Role | Size | Weight | Line Height |
|------|------|--------|-------------|
| Body | 16px (`--font-size-base`) | 400 | 1.5 |
| Label / hint | 14px (`--font-size-sm`) | 400 | 1.4 (matches existing `.transcription-options-dialog__hint`) |
| Heading (dialog titles, splash app name) | 18px (`--font-size-lg`) | 600 | 1.2 |
| Display (rare — none needed this phase; reserved) | 20px (`--font-size-xl`) | 600 | 1.2 |

Weight tokens: 400 (regular body/labels/inputs) and 600 (dialog `<h3>`, header app-name, button labels that need emphasis — e.g. primary CTA). No third weight — matches every existing dialog (`TranscriptionOptionsDialog`, `DeleteConfirmDialog`) and `Header.css`.

## Color

Existing tokens from `tokens.css`, reused as-is.

| Role | Value | Usage |
|------|-------|-------|
| Dominant (60%) | `#1a1a1a` (`--color-bg-base`) | App window background, splash window backdrop-behind-card |
| Secondary (30%) | `#242424` / `#2e2e2e` (`--color-bg-surface` / `--color-bg-elevated`) | Splash card, settings dialog, first-run setup card, progress-card backgrounds |
| Accent (10%) | `#4caf72` (`--color-accent-green`) | Reserved for: primary CTA button border+text ("Set Up Environment", "Save Settings", "Retry Setup"), progress-bar fill (setup download, model download), focus outline replacement (border-color on focused inputs uses `--color-border-focus` instead — accent is NOT used for focus rings, matching existing `input:focus` pattern), success/complete status text |
| Destructive | `#e05454` (`--color-error`) | Reserved for: setup-failure error text, model-download-failure error text, "Cancel Setup" confirmation button (mid-download cancel is destructive — discards partial download) |

Accent reserved for: primary-action button border + label text (never a filled/solid button — matches existing `--btn--primary` pattern of transparent background + accent border/text, `--color-accent-green-muted` background on hover), progress-bar fill only. Never used for body text, never used for more than one interactive element's emphasis per screen.

## New Component Inventory & Chrome Specs

Prescriptive sizing/placement so the executor doesn't have to guess. All four reuse the existing dialog/progress-bar/button chrome already proven in the codebase (`TranscriptionOptionsDialog.css`, `DeleteConfirmDialog.css`, `subtitles-page__progress-*`).

### Splash window (`packages/desktop/src/splash/`)
- Frameless `BrowserWindow`, not resizable, 360×200px, centered on primary display, always-on-top during launch only.
- Content: single card filling the window — `background: var(--color-bg-elevated)`, no border/radius needed since it fills the frameless window edge-to-edge.
- Layout: app name (Heading role, 18px/600) centered, `--spacing-md` below it a status line (Label role, 14px/400, `--color-text-secondary`), `--spacing-md` below that a progress track matching `.subtitles-page__progress-track`/`__progress-fill` exactly (4px height, `--color-bg-surface` track, `--color-accent-green` fill, 2px radius) at indeterminate/looping animation (no real percentage available pre-health-check — use a looping fill, not a static bar).
- No window chrome, no close button, no user interaction surface at all.

### First-run setup (`packages/frontend/src/components/FirstRunSetup*`)
- Renders as a full-page blocking view inside the **main app window**, not the splash window. Rationale: splash (D-05) is explicitly scoped to the brief backend-health/Remotion-bundling wait; env provisioning is a much longer (~5-6GB), resumable, user-visible flow that deserves its own dedicated in-app screen with retry affordances — conflating it with the splash window would leave users staring at a frameless, non-interactive window for minutes with no way to see errors or retry.
- Visual chrome: centered card, same family as `.transcription-options-dialog` (width 480px, `background: var(--color-bg-surface)`, `border: 1px solid var(--color-border)`, `border-radius: 8px`), but NOT a modal/backdrop overlay — it fully replaces the app content area (there is nothing usable behind it yet, since the backend can't transcribe without the venv).
- Progress bar: same `progress-track`/`progress-fill` pattern as splash, sized to card width minus `--spacing-md` padding on each side.
- Buttons: primary CTA style (`transparent` bg, `--color-accent-green` border+text) for "Set Up Environment" / "Retry Setup"; danger style (`transparent` bg, `--color-error` border+text, matching `.delete-confirm-dialog__btn--danger`) for the cancel-mid-download confirmation only.

### Settings screen (`packages/frontend/src/components/SettingsDialog*`)
- Entry point: new gear-icon button added to `Header.tsx`, placed after `TabNav` (right-aligned in the flex header row). Same button-reset pattern as `.header__app-name` (no background/border, `color: var(--color-text-primary)`, hover `color: var(--color-accent-green)`).
- Modal dialog, not a new page/tab — reuses the exact `TranscriptionOptionsDialog` chrome: backdrop `rgba(0,0,0,0.6)` at `z-index: 2000`, card `background: var(--color-bg-surface)`, `border: 1px solid var(--color-border)`, `border-radius: 8px`, `width: 480px`, header/body/footer three-part layout with `1px solid var(--color-border)` dividers, `--spacing-md` padding throughout.
- Form fields use `.transcription-options-dialog__field` input styling (`background: var(--color-bg-elevated)`, `border: 1px solid var(--color-border)`, `border-radius: 4px`, focus → `border-color: var(--color-border-focus)`).
- Footer buttons: secondary ("Cancel") + primary ("Save Settings") using the exact `--btn--secondary`/`--btn--primary` pair already defined in `TranscriptionOptionsDialog.css`.

### Model-download progress
- No new component — extend the existing `subtitles-page__progress-card` state already rendered in `SubtitlesPage.tsx` for upload/transcribe progress. Add a new status branch reusing the identical `progress-card` → `progress-track` → `progress-fill` DOM structure and class names, just a different status label string (see Copywriting Contract above). Do not create a parallel progress-bar component.
